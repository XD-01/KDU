# WindowsInfo 内核驱动 + Intel VT-x/EPT / AMD SVM/NPT Hypervisor

本仓库只保留 Windows x64 内核驱动及其 Hypervisor/EPT 实现。用户态 GUI、
云端下发、授权、打包脚本和 KDU 加载器均已移除；驱动通过 IOCTL 协议对外
提供能力，加载方式由使用者自行选择。

## 能力概览

### 标识下发

管理员态客户端打开**按启动周期派生的控制设备**（不再有 `\\.\WindowsInfo`
固定入口），用 `HWID_IOCTL_APPLY_CONFIG` 下发 `HWID_CONFIG` 块。派生算法见
文末“加载与调用”。驱动按模块应用并返回覆盖报告：

- SMBIOS Type 0/1/2/3/4/17 字段（厂商、产品名、版本、序列号、UUID、SKU、
  资产标签等）；
- 物理磁盘 / 光驱序列号、`MSFT_PhysicalDisk.UniqueId`、卷序列号；
- 网卡当前 / 永久 MAC 与 `NetworkAddress`；
- GPU UUID 与板卡序列号；
- CPU ProcessorId；
- `MachineGuid`、`ProductId`、`ComputerName` / `HostName` 等注册表值；
- **v4 新增**：PnP 设备实例 ID / 硬件 ID / 兼容 ID（`IRP_MN_QUERY_ID`）、
  `HKLM\SYSTEM\CurrentControlSet\Enum` 下的 `DeviceDesc` / `FriendlyName` /
  `HardwareID` / `CompatibleIDs`、`HKLM\HARDWARE\DESCRIPTION\System\
  CentralProcessor\N`（`ProcessorNameString` / `VendorIdentifier` /
  `Identifier`）、ACPI 表头（`OEMID` / `OEM Table ID`，就地改写物理表并重算
  校验和）、显示器 EDID 序列号（4 字节 ID + 描述符字符串 + 校验和）、
  GPT 磁盘 GUID（`DiskId`）与分区 GUID（`PartitionId`，走
  `IOCTL_DISK_GET_DRIVE_LAYOUT_EX` / `IOCTL_DISK_GET_PARTITION_INFO_EX`）。

`HWID_IOCTL_QUERY_COVERAGE` 返回每个模块实际安装的挂钩数、改写次数、
覆盖路径（固件表、注册表、IOCTL、OID、SCSI 直通、厂商 IOCTL、
`STORAGE_DEVICE_DESCRIPTOR`、固件表查询、文件系统卷信息）以及捕获到的
原始标识符。覆盖报告第 11 项（`HWID_MODULE_HIDE`）专门上报隐蔽姿态：
`RewriteCount` 是姿态位掩码（设备摘名 / 模块表摘链 / PE 头擦除），
`HookCount` 是当前仍挂着的外部派发挂钩总数（0 表示没有任何派发表改动，
最不容易被内核扫描器发现）。

### CPUID 品牌串（v5）

`Win32_Processor.Name`、`ProcessorId` 以及几乎所有指纹库的 CPU 型号，都直接来自
CPUID `0x80000002..0x80000004` 三片叶子拼出的 48 字节品牌串。注册表
`ProcessorNameString` 只是一份缓存，改它不会影响 CPUID 本身，所以下发
`HWID_FIELD_CPU_NAME` 时会同时做两件事：

1. `Cpu` 模块写注册表（`HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\N`）；
2. `Hv::SetCpuBrand()` 把同一份值交给 hypervisor，在 CPUID 退出里覆盖那三片叶子。

要点：

- **必须先 `APPLY_CONFIG` 再 `HV_START`**。后端在建 VMCS/VMCB 时决定是否拦截
  CPUID，运行中改标志不生效；顺序反了 `SetCpuBrand()` 返回失败并写日志
  （`Report.LastError = 16`）。要补下发就 `HV_STOP` → `APPLY_CONFIG` → `HV_START`。
- **两个后端默认都不拦截 CPUID**：原生结果与裸机逐字节一致，也没有退出延迟，
  这是默认姿态。只有下发了品牌串才打开 `CPUID` 拦截位（Intel：主控位 bit1；
  AMD：拦截字 bit18），此时每次 CPUID 都会产生一次 VM-exit —— 品牌串本身对得上，
  但 CPUID 的往返延迟会变成可测量特征，这是打开该功能的固有代价。
- 顺带修掉一个问题：Intel 侧 `HandleCpuid()` 之前是死代码 —— 主控位里根本没有
  打开 CPUID 退出，所以「清 leaf1 ECX bit31」那行从未执行过。现在它在下发品牌串
  时才会被打开，其余时间仍保持不拦截。
- 尾部按空格填充，不放 `NUL`：真实品牌串是空格填充，出现 `NUL` 反而是人造痕迹。
- 未启动 hypervisor（没调 `HV_START`）时品牌串不生效，只有注册表那一层是假值。

### v4 覆盖路径的三个已知限制

1. **PnP QUERY_ID 改写发生在完成例程里**，不是在 `original()` 返回之后。
   原因：`IoCompleteRequest` 会先唤醒等待线程再返回，返回后再改缓冲区
   会让调用方有几百纳秒的窗口读到原值，换缓冲路径甚至可能让它拿到即将
   被 `ExFreePool` 的指针。完成例程运行在唤醒之前，这条路径没有竞态；
   代价是改写时处于 `DISPATCH_LEVEL`，只能用非分页池与内存拷贝。
2. **Enum 键改写会影响重启后的 PnP 匹配**：`HardwareID` / `CompatibleIDs`
   是驱动匹配依据，改写后重启时设备可能被重新判定。所有写入都走
   `Reg::ApplyBatch`（备份 + journal），关机/卸载时还原；备份读不到时
   直接跳过写入，不会写坏。**EDID 是残留风险最高的一项**：它按
   `REG_BINARY` 直写（`ApplyBatch` 的字符串通道会把 128 字节二进制扩成
   WCHAR 垃圾），靠模块内 16 槽备份在 `Shutdown()` 还原，异常掉电时
   假 EDID 会留到下次卸载。
3. **ACPI 只改物理表**：Windows 启动期已把 DSDT/SSDT/FACP 的 OEMID、
   OEM Table ID 缓存进 `HKLM\HARDWARE\ACPI\*`（键名本身就是这两个 ID），
   我们的改写不会回灌这些缓存，所以 `EnumSystemFirmwareTables` 与注册表
   路径可能仍返回原值；直接扫固件/物理内存的指纹读取器才会看到假值。
   另外 `FACS` 被主动跳过（没有标准头，写它会破坏 S3 恢复路径）。

### Hypervisor / EPT / NPT

`HWID_IOCTL_HV_START` 会按 CPU 厂商启动对应的晚加载（late-launch）
Hypervisor：Intel 使用 VT-x + EPT，AMD 使用 SVM + NPT。两条都是真实执行
路径，不是“只检测、不启动”：

1. 在当前 CPU 校验厂商能力：
   - Intel：VT-x、`IA32_FEATURE_CONTROL`、`IA32_VMX_BASIC`、EPT 能力
     （4 级页表、WB 内存类型、2 MiB 页、INVEPT）、CR0/CR4 固定位；
   - AMD：CPUID `0x80000001.ECX[2]`（SVM）、CPUID `0x8000000A`
     （NPT、可用 ASID 数量）、`VM_CR.SVMDIS`、EFER.LME；
   - 两者都要求 CPUID 未报告其他 Hypervisor、未启用 LA57。
2. 为每个逻辑 CPU 分配 4 KiB 对齐的控制块（Intel VMXON + VMCS，AMD
   VMCB + 宿主保存区）、独立宿主栈和 FXSAVE 区域；建立共享的 1 TiB
   二级页表 identity map（Intel EPT / AMD NPT，2 MiB 大页，RAM 使用
   WB，MMIO/固件区使用 UC/PCD）。
3. 通过 `KeIpiGenericCall` 在每个逻辑 CPU 上完成 Intel
   `VMXON`/`VMCLEAR`/`VMPTRLD`/`VMLAUNCH` 或 AMD `EFER.SVME` +
   `VMSAVE` + `VMLOAD` + `VMRUN`。操作系统本身成为 guest，所有 CPU
   持续运行在非根 / guest 模式，直到 HV_STOP。
4. 退出处理：
   - 外部中断、NMI、MSR、I/O 端口、CR/DR 访问默认透传给 guest，不产生
     退出；AMD 的 VMRUN/VMLOAD/VMSAVE/STGI/CLGI/SKINIT 被拦截并注入
     `#UD`，guest 无法借此逃逸；
   - **CPUID 不改变结果**：AMD 路径完全不拦截 CPUID（零退出、与裸机完全
     一致）；Intel 硬件强制 CPUID 产生 VM-exit，处理器直接返回原生
     CPUID 值，不再改写 `0x40000000` 范围，结果与裸机逐字节一致；
   - Intel EPT violation / AMD NPF：对通过 `HV_SET_PAGE` 登记且权限不足
     的页向 guest 注入 `#GP`；对未登记页做自愈放行；无法映射的 GPA 在
     内核态退出虚拟化继续执行，在用户态则注入异常，避免在 KVA shadow
     用户页表下切换宿主 CR3；
   - 任何无法安全恢复的内核态退出（EPT/NPT 配置错误、未知退出、AMD
     VMCB 无效等）：Intel 执行 `VMXOFF`、AMD 清除 `EFER.SVME`，恢复
     guest 上下文并用 `IRETQ` 原地继续执行；用户态异常注入 `#GP/#UD`
     后继续执行（fail-safe，不会把系统留在半虚拟化状态）。
5. 宿主侧使用 System 进程页表和独立的每 CPU 宿主栈；捕获 CR3 前会完成
   所有动态分配，并逐页验证代码、宿主栈、控制块、FXSAVE 区与 EPT/NPT 表在
   System 页表中均可访问。Intel 使用 PCID 0，AMD 使用每 CPU 的
   `VM_HSAVE_PA` 宿主保存区保存 FS/GS/TR/LDTR/MSR 状态。
6. `HWID_IOCTL_HV_STOP`：向所有 CPU 广播超调用（Intel `VMCALL` / AMD
   `VMMCALL`），逐 CPU 退出虚拟化后释放全部表、控制块与栈。

`HWID_IOCTL_HV_SET_PAGE` 把目标 2 MiB 页拆成 4 KiB 页并设置 R/W/X 权限：
Intel 通过 `INVEPT`、AMD 通过 VMCB `TLB_CONTROL` 在所有在线 CPU 上刷新
TLB。最多登记 64 个页策略；被拒绝的访问会在 guest 中触发 `#GP`。

> **AMD 说明**：AMD 路径是完整的 VMRUN/NPT 实现，包含 VMCB 状态保存与
> 恢复、每 CPU 宿主保存区、NPT 拆页与权限、SVM 指令拦截和退出处理。
> 此外通过 8 KiB MSRPM 只拦截会暴露/破坏虚拟化的 MSR，并用 per-vCPU
> shadow 让 guest 看到与裸机一致的值。它要求 `VM_CR.SVMDIS=0`、NPT
> 可用、至少 2 个 ASID，且 CPUID 未报告已有 Hypervisor；任一条件不满足时
> `HV_START` 返回失败（fail-closed），不会半启动。与 Intel 路径一样，当前
> CI 只验证编译与链接，运行行为仍需在真机/快照上验证。

### 隐蔽性：已隐藏与无法隐藏的部分

已处理的“主动暴露”：

- **CPUID**：AMD 路径完全不拦截 CPUID（零 VM-exit、结果与裸机逐字节
  一致）；Intel 硬件强制 CPUID 退出，但处理器直接返回原生值，不再写
  hypervisor 位、不再伪造 `0x40000000` 叶子。
- **Intel `CR4.VMXE`**：通过 CR4 guest/host mask + read shadow 隐藏，
  guest 默认读到 0；guest 写 CR4 时由退出处理按裸机语义模拟，Windows
  正常的 CR4 写入不会产生额外退出。
- **Intel VMX 指令/能力 MSR**：`RDMSR 0x480-0x490` 在非根模式下没有裸机
  语义，现由 MSR bitmap 拦截并从根模式返回真实值；VMXON/VMLAUNCH/
  VMREAD/VMWRITE/INVEPT/INVVPID 等按裸机语义注入 `#UD`，不会再因为
  探测导致 `VMXOFF`。
- **AMD SVM MSR**：`RDMSR EFER` 返回 `SVME=0、LMA=1`；`VM_HSAVE_PA`
  返回 0 或 guest 自己写入的 shadow；`VM_CR` 读写走 per-vCPU shadow，
  guest 既看不到宿主 SVME/HSAVE 状态，也无法真正关闭 SVM。
- **超调用**：改用 `VMCALL`（Intel）/`VMMCALL`（AMD），二者在裸机上都是
  非法指令；不再占用 CPUID 叶子，非 magic 调用按裸机语义 `#UD`。

仍然可被检测、无法消除的部分（架构限制）：

- **Intel CPUID 必然 VM-exit**：这是 VMX 非根模式的硬件行为，没有关闭
  开关。用户态或内核态都可以用 `RDTSC/RDTSCP` 测量 CPUID 延迟来发现
  Hypervisor，即使返回值完全一致。
- **Intel VMXON 探测**：guest 若先写 `CR4.VMXE=1`（我们按裸机语义让写入
  成功并更新 read shadow），再执行 VMXON，会被 `#UD` 拒绝；裸机上则可
  成功。晚启动 Hypervisor 无法既隐藏自己又允许嵌套 VMX。
- **AMD 主动探测**：guest 先 `WRMSR EFER.SVME=1` 再执行 `VMRUN`，裸机
  会进入嵌套虚拟化，我们只能 `#UD`。
- 性能计数器、缓存/TLB 微基准、SMM/固件层检测等同样能观察到虚拟化的
  时序差异。
- **驱动控制面**：控制设备没有 `\DosDevices` 符号链接，名称按 BootId 派生，
  不在 `\??` 中留下固定入口；调用 `HWID_IOCTL_CONCEAL` 后连 `\Device` 目录
  里也查不到该对象。但是：
  - disk / NIC / GPU / mssmbios / PnP 派发挂钩仍然可见 —— 只要内核扫描器
    遍历某个已知驱动对象的 `MajorFunction[]`，就会看到指向无主映像的指针。
    这是“外部驱动 + 派发表hook”这一路线的固有暴露面，除非改成内联 hook 或
    完全用 EPT 拦截，本仓库没有做；
  - 手动映射的代码页是“无映像 backing 的可执行非分页内存”，物理内存扫描 /
    PFN 数据库遍历可以发现；
  - 映像里仍有少量明文串（驱动名、注册表路径、日志前缀），可被内存扫描命中。
  因此本仓库的隐蔽目标是“被动枚举与常规扫描看不到控制面和 pool 特征”，
  不是“对所有内核扫描器都不存在”。

因此目标是“被动枚举与常规检测看不到 HV 痕迹”，而不是承诺对所有主动
探测都不可见。

## 技术路线：PG 隔离与加载后脱链

### 1. 关于“第二个 VTL”

Windows 的 VTL0/VTL1 是 VBS/Hyper-V 的虚拟信任级别：VTL1 由 Microsoft
Hypervisor + Secure Kernel 建立，普通内核驱动没有创建 VTL 的接口。本项目
的 Hypervisor 是晚启动的 L0（VMX/SVM root），并且 `HV_START` 明确拒绝在
已有 Hypervisor（Hyper-V/VBS/嵌套虚拟化）下启动。因此：

- “一个 VTL 做硬件 ID、另一个 VTL 隔离 PG”在当前架构下无法实现；
- 真 VTL1 需要切换到 Hyper-V/VBS 体系，与 KDU 手动映射、晚启动 HV 互斥，
  不属于本驱动能完成的范围；
- 可行的替代：
  1. 继续使用 kurasagi/theiapg 做 PG 绕过（当前路线）；
  2. 在同一个 HV 内做“PG 双视图”（EPT/NPT 对 PG 返回原始页、对其他代码
     返回修改页，或按 RIP 拦截 PG 校验）。属于研究级实现，不能承诺稳定，
     也会引入新的可检测时序；
  3. 只做下面这种“加载后脱链”，不碰 PG 监控的核心结构；风险最低，但
     不能保证 PG 一定不检测到模块表/PE 头修改。

### 2. 加载后脱链（已实现）

`DriverEntry` 末尾自动调用 `Hide::DetachAtLoad()`（手动映射擦 PE 头；服务
加载的模块表摘链留到设备打开后）；新增 `HWID_IOCTL_DETACH`
（`0x222024`）供 loader 在打开设备后触发完整脱链（幂等）。

| 加载方式 | 行为 |
| --- | --- |
| KDU/kdmapper 手动映射 | `RtlPcToFileHeader` 找不到本模块 → 不在 `PsLoadedModuleList`；清零 PE 头（临时清 CR0.WP），使内存扫描器无法按 MZ/PE 解析。KDU 若已擦头则自动跳过 |
| 作为真实服务加载 | 通过 `DRIVER_OBJECT::DriverSection` 取得本映像的 `KLDR_DATA_TABLE_ENTRY`，校验 `DllBase` 精确匹配后从 `PsLoadedModuleList` 摘链；**不擦 PE 头**（内存管理器仍持有 section） |

控制设备不删除（客户端需要继续访问）；摘链只针对模块表/PE 头。

风险：在没有 PG 绕过的系统上修改 `PsLoadedModuleList` 可能被 PatchGuard
检测；该路径只应在你确认 PG 已关闭/隔离时使用。

### 3. PiDDBCacheTable / CI 审计缓存 / MmUnloadedDrivers

这三类表**只在“服务方式加载/卸载过驱动”时才会有本驱动的条目**；KDU
手动映射不经过 I/O 管理器的驱动数据库和 CI 加载路径，因此驱动里没有默认
实现（避免在错误 build 上误摘链）。需要时按下面模板在 `Hide::Detach()`
末尾接入，并对目标 Windows build 校准签名：

```c
// 1) 在 ntoskrnl 的 .text/.data 里按 build 签名定位全局变量
//    PiDDBCacheTable       -> RTL_AVL_TABLE*
//    g_KernelHashBucketList-> LIST_ENTRY*
//    MmUnloadedDrivers     -> _UNLOADED_DRIVERS[] / MmLastUnloadedDriver
static PVOID FindPattern(PVOID base, SIZE_T size,
                         const UCHAR* pattern, const char* mask);

// 2) PiDDBCacheTable：只删除 DriverName 与本驱动文件名一致、且
//    TimeDateStamp 与 PE 头一致的表项；用 RtlDeleteElementGenericTableAvl
//    或（若表项同时挂在 LIST_ENTRY 上）RemoveEntryList。找不到就跳过。
typedef struct _MY_PIDDB_ENTRY {
    LIST_ENTRY List;          // build-specific；部分版本是 AVL 节点
    UNICODE_STRING DriverName;
    LARGE_INTEGER LoadTime;
    ULONG TimeDateStamp;
    NTSTATUS LoadStatus;
} MY_PIDDB_ENTRY;

// 3) CI hash bucket（_RTL_DYNAMIC_HASH_TABLE / bucket list）：
//    删除 FileName 等于本驱动文件名（或 ImageHash 等于本映像哈希）的 bucket。
//    不同 build 的 bucket 头布局不同，必须先验证链表边界和名字指针可读。

// 4) MmUnloadedDrivers：固定大小数组（通常 50 项）。
//    仅清空 Name 与本驱动一致、或 StartAddress/EndAddress 覆盖本映像范围的项，
//    同时把 MmLastUnloadedDriver 回退到上一个有效项。
```

安全规则（必须遵守）：

- 每一层都做“精确匹配”（映像基址、驱动文件名、TimeDateStamp/哈希），
  任意一项对不上就跳过，绝不按单一名字模糊删除；
- 先验证指针可读（`MmIsAddressValid`）和链表边界，再摘链；
- 最好在系统刚启动、目标表无并发修改时执行；这些表的内核锁未导出，运行时
  摘链存在竞态；
- 修改 CI/PiDDB 表属于反审计行为，可能触发 PatchGuard/CI 告警；只有在你
  确认目标环境允许时才启用。

### 4. loader（KDU/kdmapper）需要配合的改动

1. 映射完成后打开派生的控制设备（见“加载与调用”），完成配置下发；
2. 可选调用 `HWID_IOCTL_DETACH`（幂等；`DriverEntry` 已自动执行一次）；
3. 如果新增“删除控制设备对象/对象目录项”的需求，需要改成“先打开并持有
   句柄，再通知驱动脱链”的流程；当前实现刻意保留设备，避免客户端断连；
4. 若 loader 已经擦除 PE 头，驱动的自动发现会跳过擦头步骤，不会二次破坏；
5. 若要清理 PiDDB/CI/MmUnloaded，建议在 loader 侧完成（loader 更清楚
   驱动文件路径、时间戳与哈希），或把签名/结构按目标 build 填进
   `Hide::Detach()`。

### Hypervisor 控制页遮盖（decoy remap）

逐条拦截“读取”不是可行方案：那会让每次访存都变成 VM-exit，性能和时序
特征都会暴露 Hypervisor 本身。这里改用**第二级页表视图替换**：

- 在 EPT/NPT 中把 HV 私有控制页的 4 KiB 叶映射到**每页独立的零页
  （decoy）**：guest 读取看到全零，写入落在 decoy，不会泄漏 VMCB/VMCS
  内容；
- 宿主在 host CR3 下仍然访问真实页，VMRUN/VMLAUNCH、MSRPM、MSR bitmap、
  宿主保存区都由硬件按物理地址读取，**不受 EPT/NPT 影响**；
- 每个隐藏页使用独立 decoy，避免扫描器“写一个地址、在另一个隐藏地址读到
  同样内容”的共享页检测；
- 遮盖发生在任何 VMRUN/VMLAUNCH 之前；失败则 `HV_START` 直接失败
  （fail-closed）。

当前已遮盖：VMCB、宿主保存区、MSRPM、每 CPU 宿主栈与 FXSAVE 区（AMD）；
VMXON 区、VMCS、MSR bitmap、每 CPU 宿主栈与 FXSAVE 区（Intel）。宿主栈和
FXSAVE 已改为独立、页对齐连续内存，不会连带隐藏相邻池分配。仍未遮盖：
NPT/EPT 表本身、policy 表和 Vcpu 数组；这些在 README 中明确列出，不做虚假
承诺。

> 该设计使 guest 对这些 VA 的读取不再产生任何 VM-exit；检测面仅剩
> “某些内核 VA 读出全零”这一间接迹象，以及可以读取 NPT/EPT 表的定向
> 扫描器（需要先获得表根物理地址）。仍必须在真机上验证。

### SSDT 守卫

`Guard.cpp` 通过替换 SSDT 中的 `NtOpenSection` 拒绝用户态打开
`\Device\PhysicalMemory`。约束：

- **需要显式确认码**：`HWID_GUARD_REQUEST.Enable = 1` 时
  `Reserved` 必须等于 `HWID_GUARD_ACK_PG_OFF`（`'PGOF'`），否则
  `STATUS_INVALID_PARAMETER` 直接拒绝。内核没有可靠的“PG 是否在线”
  查询接口，所以这里不猜状态，只拒绝误操作 —— 客户端写错一个字段不会
  把机器打蓝。关闭（`Enable = 0`）不做校验，任何时候都能关。
- 仅在 PatchGuard 已被绕过时启用，否则会触发系统完整性检查（PG 在线时
  改完 SSDT 后 5–10 分钟内 `0x109 CRITICAL_STRUCTURE_CORRUPTION`）；
- x64 服务表项是 16 字节粒度的 32 位偏移，驱动映像必须位于服务表
  ±128 MiB 范围内；超出时守卫直接返回失败并保持原表不变；
- 未启用时完全不修改 SSDT，卸载/关机时恢复原入口。

除了这个守卫，驱动的其它所有改动（派发表钩子、`PsLoadedModuleList`
摘链、注册表写入、SMBIOS/ACPI 就地改写）**都不在 PatchGuard 的校验面内**，
所以常规部署（不开守卫）本身不需要关 PG，也不会因为 PG 蓝屏。真正需要
`\Device\PhysicalMemory` 也读不到本驱动页面时，正确路线是 EPT 双视图
（不同 EPTP 给不同访问者不同页面），而不是改内核代码或 SSDT —— 本仓库
只实现了 EPT 基础设施（`HV_SET_PAGE` 拆页 + 权限），没有实现 EPTP 切换。

## IOCTL 协议

所有请求都是 `METHOD_BUFFERED`、`FILE_ANY_ACCESS`、设备类型 `0x22`，
且只允许管理员调用。

| IOCTL | 值 | 方向 | 说明 |
|---|---:|---|---|
| `HWID_IOCTL_APPLY_CONFIG` | `0x222004` | 输入 | 下发 `HWID_CONFIG` |
| `HWID_IOCTL_QUERY_STATUS` | `0x222008` | 输出 | 查询 `HWID_STATUS` |
| `HWID_IOCTL_QUERY_COVERAGE` | `0x22200C` | 输出 | 查询 `HWID_COVERAGE_REPORT` |
| `HWID_IOCTL_HV_START` | `0x222010` | 无 | 启动全 CPU VT-x+EPT 或 SVM+NPT |
| `HWID_IOCTL_HV_STOP` | `0x222014` | 无 | 停止虚拟化并释放所有表 |
| `HWID_IOCTL_HV_STATUS` | `0x222018` | 输出 | 查询 `HWID_HV_REPORT` |
| `HWID_IOCTL_HV_SET_PAGE` | `0x22201C` | 输入 | 拆分 4 KiB 页并设置 EPT/NPT 权限 |
| `HWID_IOCTL_SET_GUARD` | `0x222020` | 输入 | 启用/关闭 SSDT 守卫 |
| `HWID_IOCTL_DETACH` | `0x222024` | 无 | 再次执行加载后脱链（幂等） |
| `HWID_IOCTL_CONCEAL` | `0x222028` | 无 | 摘掉控制设备的对象名（必须在客户端已持有句柄后调用，幂等） |

结构体定义、字段宽度与对齐要求以
[`driver/WindowsInfo/SpooferIoctl.h`](driver/WindowsInfo/SpooferIoctl.h)
为准。`HWID_HV_REPORT` 固定为 12 个 32 位字段（48 字节），驱动内有
编译期断言防止布局漂移；`Flags` 位定义（`HWID_HV_FLAG_*`）也在同一
头文件中。

`HWID_STATUS` 的三个保留字段现在有了含义：`Reserved[0]` = 隐蔽姿态位
（`HWID_STEALTH_DEVICE_CONCEALED` / `LIST_UNLINKED` / `HEADERS_ERASED`），
`Reserved[1]` = 当前外部派发挂钩数量，`Reserved[2]` = 池标签（用于确认
部署的是哪一份映像）。

- Windows 10 / 11 x64

  `Microsoft.DriverKit.Build.Tasks.*.dll`）

build_driver.bat

## 加载与调用

驱动支持两种方式：

- KDU 内存映射：`kdu.exe -map driver\x64\Release\WindowsInfo.sys`
- kdmapper 等手动映射：`DriverEntry` 在 `DriverObject == NULL` 时会先调用
  `IoCreateDriver` 创建合法驱动对象，再继续初始化。

加载后**没有 DOS 符号链接，也没有固定设备名**。设备名由当前启动周期的
`BootId` 与 `HWID_DEVICE_SALT` 派生：

```text
boot_id = HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\
          Memory Management\PrefetchParameters 的 REG_DWORD "BootId"
seed    = ((uint64)boot_id << 32) ^ 0x9E3779B97F4A7C15
hash    = FNV-1a-64(seed 的 8 个小端字节)
name    = \Device\<hash 的 16 位小写十六进制>
```

管理员客户端用 `\\?\GLOBALROOT\Device\<16 hex>` 打开（Python 示例）：

```python
import struct, winreg
key = winreg.OpenKey(winreg.HKEY_LOCAL_MACHINE,
    r"SYSTEM\CurrentControlSet\Control\Session Manager\Memory Management\PrefetchParameters")
boot_id = winreg.QueryValueEx(key, "BootId")[0]
seed = ((boot_id & 0xFFFFFFFF) << 32) ^ 0x9E3779B97F4A7C15
h = 0xcbf29ce484222325
for b in struct.pack("<Q", seed & 0xFFFFFFFFFFFFFFFF):
    h = ((h ^ b) * 0x100000001b3) & 0xFFFFFFFFFFFFFFFF
device = r"\\?\GLOBALROOT\Device\%08x%08x" % (h >> 32, h & 0xFFFFFFFF)
```

`BootId` 缺失时按 0 处理（名称退化为固定值，但仍然没有 `\??` 符号链接）。

> 同一启动周期内重复映射会得到同一个名字并返回
> `STATUS_OBJECT_NAME_COLLISION`。旧实现用指针后缀规避，但那样也会让
> 设备名可预测；现在请重启后再映射，或先确认旧实例已卸载（手动映射的
> 驱动通常不会执行 `DriverUnload`）。

典型调用顺序：

```text
APPLY_CONFIG -> QUERY_COVERAGE -> [HV_START -> HV_STATUS -> HV_SET_PAGE]
             -> [SET_GUARD true] -> ... -> [SET_GUARD false] -> HV_STOP
```

所有 IOCTL 都会先校验调用者令牌是否属于管理员组，非管理员返回
`STATUS_ACCESS_DENIED`。驱动初始化完成前设备返回 `STATUS_DEVICE_NOT_READY`。

## 运行限制与安全设计

- 仅支持 x64；最多 256 个逻辑 CPU。
- EPT/NPT identity map 覆盖 1 TiB guest-physical 地址；RAM 超过 1 TiB 或
  存在 1 TiB 以上的 MMIO 时，HV_START 会失败或对应访问会让该 CPU 安全
  退出虚拟化。
- 要求 CPUID 未报告其他 Hypervisor；Hyper-V、VBS/HVCI、嵌套虚拟化环境
  下 HV_START 返回失败，不会与已有 Hypervisor 争抢 VMX/SVM。
- Intel 要求 BIOS 已锁定 `IA32_FEATURE_CONTROL` 且允许 VMXON outside SMX；
  要求 4 级 EPT、WB 内存类型、2 MiB 页和 INVEPT。
- AMD 要求 `VM_CR.SVMDIS=0`、NPT、至少 2 个 ASID、EFER.LME，并且
  `EFER.SVME` 未被其他组件占用。
- 两条路径都要求 LA57 未启用。
- 不处理 CPU 热插拔与睡眠/休眠：HV_START 后请先 HV_STOP 再进入睡眠、
  休眠或热插拔 CPU。
- 第三方驱动 IRP hook 没有跨模块的全局调用 drain。手动映射部署必须让映像
  常驻，不能在 `UnhookAll()` 后立即释放代码页；若改为服务卸载，需要另行
  实现所有 hook 的引用计数与 CPU/IPI 屏障，否则在途 IRP 可能返回已释放代码。
- 任何无法安全恢复的内核态 VM-exit、VM-entry 失败、EPT misconfiguration
  或 AMD VMCB 无效，都会让当前 CPU 通过 VMXOFF（Intel）或清除
  `EFER.SVME`（AMD）+ IRETQ 回到原生执行；用户态异常退出则注入 `#GP/#UD`
  后继续。设计上避免 Hypervisor 自身错误演变为蓝屏，但可能降级为
  “部分 CPU 已退出虚拟化”，可通过 HV_STATUS 的
  `HWID_HV_FLAG_DEGRADED` 观察；仍需在目标机快照中验证。
- 守卫依赖 SSDT 可写范围与 PatchGuard 已关闭；任一条件不满足时安全失败。
- 本仓库不包含签名、测试签名开启、PatchGuard 绕过或加载器；请自行准备。

**本轮稳定性审计已修复**：未启动 CPU 的原生 hypercall、AMD 首次 VMRUN
失败后 GIF 未恢复、Intel 启动/停止后 CR4.VMXE 泄漏、SMBIOS 3.x EPS 长度
误判、hook 发布窗口、IRP pending 传播、关机与 IOCTL 竞态、journal 长度/
字符串边界、RAM 边缘 4 KiB 页错误保持 UC、4 GiB 以上地址对齐掩码，以及
CR3 验证线程超时后的 UAF。RAM 边缘现在拆成 4 KiB，仅真实 RAM 页为 WB，
同一大页内的 MMIO/空洞继续为 UC。

**验证状态**：驱动已在 Windows Server 2022 + WDK 26100 上完成编译与链接
（产物为有效 PE32+ x64 `.sys`）。这不等于运行时验证。必须在授权的
Intel 与 AMD 真机/可回滚快照上分别覆盖：首次启动、启动失败注入、重复
START/STOP、全 CPU 异常退出后的降级/重启、4 GiB 以上及非 2 MiB 对齐 RAM、
高频 CPUID/RDMSR、HV_SET_PAGE 后访问与刷新、关机/卸载和配置并发、睡眠/
休眠禁止路径，以及 VMCS/VMCB/宿主栈 decoy 读取为全零但系统功能不变。
未执行这些实机矩阵前，不能承诺“绝不蓝屏”或“所有检测均不可见”。
